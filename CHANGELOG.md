# Changelog

All notable changes to this project are documented here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- **Behavior change: `pipeline-worker review --branch <name>` now approves the MR/PR when its review came back clean.** The command gains a final `approve` step, and it fires only on affirmative evidence from the two stages before it: the review looked at a real diff and raised nothing at or above `reviewMinSeverity`, *and* nothing in the open comment threads was something the agent had to **confirm** (a **correction** does not block — that point was raised and refuted), *and* the forge reports no merge conflicts against the target branch. Every other path leaves the MR/PR unapproved, including the quiet ones: a stage that was skipped, that failed, or that found something it then could not post is never "clean", because "we could not look" must not read the same as "we looked and it was fine". **Only the explicit `review` command ever approves** — `run`/`resume` do not, since a run reviewing the diff it just wrote and then approving its own MR/PR is a rubber stamp, not a review. New setting **`reviewApprove`** (default `true`, the only default-on review setting: typing `review --branch X` is already the opt-in) turns it off. Best-effort like the rest of the review: both forges reject approvals for reasons no caller can fix — **GitHub bars an account from approving its own pull request**, which is the common case when pipeline-worker opened it (point it at a separate reviewer token to make this land), and **GitLab's approvals API is paid-tier** and answers 404 on Free — and either refusal becomes a note rather than a failed run. New forge member `approveMr` on both implementations (GitLab `POST /merge_requests/{iid}/approve`, GitHub `POST /pulls/{n}/reviews` with `event: "APPROVE"`).

- **Behavior change: `pipeline-worker review --branch <name>` now also answers the comments already on the MR/PR, instead of only adding its own.** After posting its line-anchored findings, the review reads every *open* comment thread on the merge request — human review comments, plain discussion threads, and the findings scanner bots post (**SonarQube and Checkmarx are recognized and labelled as such in the prompt**) — and replies where a reply is worth reading. Two kinds, and only two: it **confirms** a thread that names a real problem in the diff at or above `reviewMinSeverity` and says what the fix is, or it **corrects** a thread that sends the author to the wrong place (a wrong line, a misread, a scanner false positive, a suggestion that should not be followed here) with a reply that opens `This is not recommended because: …`. A correction is posted regardless of severity — the floor gates confirmations only, since a wrong steer left standing costs the author time whatever it was pointing at. Replies are threaded (GitLab discussion notes, GitHub review-comment replies); a GitHub PR-level comment, which has no thread of its own, gets a new top-level comment quoting the original. Resolved threads are never read, and pipeline-worker's own comments and replies are never answered, so running `review` twice does not make it argue with itself. At most `reviewMaxComments` replies per run, most severe first. **This runs for the explicit `review` command only** — the automatic review inside `run`/`resume` still just reviews the diff, since an MR/PR it opened seconds ago has nothing to answer. Best-effort throughout: a forge that will not list comments, an agent that answers with prose, a rejected reply — each becomes a note, and the command's outcome is unchanged. No new settings.

- **`"agent": "pi"` now always runs with `--provider github-copilot`.** Pi's own model ids under that provider (e.g. `gpt-4.1`, `claude-sonnet-4.5`) don't line up with the `haiku`/`sonnet` aliases the rest of the config uses, so `intentModel`/`reviewModel` no longer default to a guessed alias for pi (or `little-coder`, which takes pi's flags) — both now default to empty, meaning no `--model` flag is sent and pi's own default is used, and you enter a model id manually in `~/.config/pipeline-worker/config.json` to pin one. **Behavior change:** this also removes a hardcoded `model: 'haiku'` that CI-fix and post-merge local-check-fix turns previously always sent regardless of agent — those turns now send `intentModel` too, so a pi/little-coder run no longer hands its CLI an alias it has never heard of on every fix attempt.

- **The MR/PR a run produces is now a link you can get at, not a bare `#42`.** `RunState` records the merge request's web URL as the forge reports it (so a self-hosted GitLab or GitHub Enterprise host is always right), the TUI's session timeline shows it, the run dashboard's result section ends on it, and `pipeline-worker sessions --branch <name>` prints it under the phase line. **`y` on either sessions screen copies the URL to your clipboard** using OSC 52, which the terminal itself handles — so it works over ssh, needs no clipboard binary, and adds no dependency; the URL is shown in the footer at the same time, since a terminal with OSC 52 disabled copies nothing silently. There is deliberately no "open in browser": nothing is spawned, on any platform. Runs recorded before this release have no stored URL, so one is rebuilt from your settings file (`github.repo` + `github.apiUrl`, or `gitlab.host` + a `group/project` id) — a numeric `gitlab.projectId` names no web path, and those rows show `#42 (no url recorded)` rather than a link that would 404.

- **Behavior change: a run started from the TUI can now be stopped, and its notes scrolled, while it is still running.** Until now the TUI dropped every keystroke from "Start run" until the run settled — stdin is in raw mode, so the terminal's own ctrl-C is off too, and the only way out of a run stuck watching CI was killing the terminal, which skipped the worktree cleanup and left the run's lock file behind. Keys now reach the run dashboard for the whole job: **ctrl-c twice within two seconds stops the run** (the first press arms it and says so in the footer, so a stray press can't throw away ten minutes of work), and **↑↓/PgUp/PgDn scroll back through the notes** the run has printed, which previously scrolled past unrecoverably — the buffer already held 200 lines but only ever showed a quarter-screen of them. Scrolling to the bottom resumes following new notes. A stopped run settles as `⏹ Interrupted` under exactly the policy ctrl-C applies on the plain CLI: the worktree is kept whatever stage the run reached and the dashboard prints the `pipeline-worker resume --branch <name>` command that re-enters it (see the worktree-preservation entry below) — the only difference is that the TUI stays up instead of exiting the process. The stop takes effect at the next step boundary and aborts the CI poll immediately, so cancelling during a 15-second pipeline poll takes milliseconds rather than waiting the interval out; an agent turn or a check command already running is allowed to finish first. **Nothing outside the TUI changes:** no cancel scope is ever armed for a plain CLI run, so `pipeline-worker run` keeps using real SIGINT and behaves exactly as before.

- **Behavior change: `pipeline-worker` with no arguments on a terminal now opens a TUI instead of starting a run.** The new full-screen dashboard (`pipeline-worker tui`, or bare `pipeline-worker` when both stdin and stdout are a TTY) covers four screens: **Run workflow** (ticket/target, then hands off to the usual live step dashboard), **Sessions** (browse this repo's runs, drill into a timeline, `r` to resume or `v` to review), **Settings** (every key with the value in force, whether it came from your file / repo auto-detection / the built-in default, and `?` for a paragraph on what it does — edits save immediately, `d` clears a key back to auto-detection), and a **Setup guide** that walks a new machine through forge, credentials, and agent, asking only the questions your answers make relevant and writing nothing until you confirm. **Anything non-interactive is unaffected:** any argument, or a redirected stdin/stdout, runs exactly as before — so `pipeline-worker` in a script or CI still means `run`. Use `pipeline-worker run` to reach the workflow directly on a terminal. Hand-rolled over raw stdin and the alt-screen buffer, so the dependency count is unchanged; the alt screen and cursor are restored on quit and on a crash. (A run started from inside the TUI now stays on the alt screen for its whole duration — see the entry below.)

- **A fresh worktree now gets its pre-commit hook's own toolchain ready before the first commit.** A worktree checks out tracked hook scripts (`.husky/*`, `.config/dotnet-tools.json`) but not the installed state behind them, so a hook that needs `husky`'s `core.hooksPath` wiring (`npm run prepare`, when the repo declares one) or a dotnet local tool (Husky.Net, CSharpier — `dotnet tool restore`, when `.config/dotnet-tools.json` exists) previously failed with "command not found" and aborted the run, indistinguishable from a real lint/build failure. Both are best-effort and silent on success: a missing `npm`/`dotnet` binary or a failing setup command degrades to a `console.error` warning rather than failing the run. **Husky.Net repos additionally get `dotnet husky install` after the restore** (when `.config/dotnet-tools.json` declares the `husky` tool and a `.husky/` directory exists): Husky.Net gitignores `.husky/_/husky.sh`, which every hook script sources, so a fresh worktree previously died on the first commit with `.husky/pre-commit: .: cannot open .husky/_/husky.sh: No such file` — a repo with no `package.json` at all never hit the npm-husky path. The file's existence is verified after the install, and a still-missing bootstrap is warned about up front instead of surfacing later as a failed commit stage.

- **`"agent": "little-coder"` — run the whole workflow on a local model.** New adapter for [little-coder](https://github.com/itayinbarr/little-coder) (pi plus extensions, tuned for 5-25GB models served by llama.cpp/Ollama), driven with pi's verified flag shape (`-p`, `--model <provider/id>`, `--tools`, prompt over stdin). Two settings of its own: `littleCoder.binary` (name or absolute path, since it is often run from a checkout) and `littleCoder.maxPromptChars` (default 12000, `0` disables) which trims every prompt middle-out — keeping the system instruction at the head and the JSON contract at the tail — so a small context window is never silently overrun. Pair it with a lower `reviewChunkChars`; see the README's "Running on a local model".

### Changed

- **Behavior change: the TUI now answers to vim keys and `/`, and every list marks its cursor the same way.** `j`/`k` move, `g`/`G` jump to the ends, and `ctrl-d`/`ctrl-u` page — on the home menu, the settings editor, the sessions list, the session timeline, the setup guide's pickers, and the run dashboard's notes, alongside the arrow keys that already worked. Plain `d` still resets a settings field, which is why the page keys take the modifier. **`/` filters the home menu and the sessions list** by substring, case-insensitively: ⏎ closes the input and keeps the filter (the footer shows `2 of 4`), `esc` drops it, and `q` on a filtered list clears the filter before it leaves the screen. While a query is open every letter goes into it, so `r`, `v`, `y` and `q` are characters rather than commands. Actions operate on the filtered cursor, so `r` never resumes the run that happens to sit at the same index in the unfiltered list. The selected row is now an accent bar down both edges rather than a `❯` prefix, drawn by one shared primitive that consumes the same two columns focused or not — a row no longer shifts sideways as the cursor passes over it, and the settings editor's Start-button-style `invert` highlight is gone in favor of the same treatment everywhere.
- **The TUI's palette gained the layers it was missing, and status colors are status-only.** Borders and section rules are painted in a recessive `surface2`, secondary prose in a readable `subtext0`, and the accent (frame titles, the selection bar, filter matches, the MR/PR link) in `mauve`. Previously all four jobs shared one muted grey while `sky` meant "running", "selected", "auto-detected" and "title" at once — so the frame competed with its own contents and a glance at a busy dashboard found the cursor instead of the live step. `sky` now means running, and nothing else.
- **Sessions rows show ages instead of absolute timestamps, and the columns are derived from the terminal.** `updated` reads `4m ago` / `2h ago` / `13d ago` (capped at seven characters) rather than a ~22-column locale-dependent `toLocaleString()`, and the branch column takes whatever the fixed columns leave instead of a hardcoded 34 — so an 80-column terminal keeps the clock on screen instead of clipping it, and the timeline's forty repeated date prefixes no longer bury the messages they precede. The settings editor's value column is likewise derived from the width rather than pinned at 26. Two frame bugs fell out of rendering this: a hint strip too long for the terminal used to drop the bottom border's corners entirely (it now clips the strip and keeps the frame), and the sessions strip had grown past 80 columns.
- **Only the focused home-menu item shows its description**, roughly doubling the choices visible at once; and the run dashboard's closing line uses the step tree's own glyph vocabulary (`✓` / `✗` / `!` / `■`) instead of emoji, which are double-width in most terminals while the TUI's width math counts code units.
- **Behavior change: a failed run no longer throws its worktree away, and `pipeline-worker resume` picks it up at the stage that failed.** Until now any exception removed the run's worktree and its temp directory on the way out, so a run that died committing (a pre-commit hook, a lost token, a forge 500) left nothing but the caller's original uncommitted changes to start over from: the rebase onto the target branch, the replayed diff, the passing checks, and the agent turn that inferred the intent were all thrown away and paid for again. The worktree is now removed on exactly one outcome — a run that finishes — and every other exit (failure, escalation, ctrl-C, a stop from the TUI) leaves it on disk and prints `resume with: pipeline-worker resume --branch <name>`. Each stage records the phase it completed (`RunPhase` gains `apply` and `commit`) along with the captured intent, check verdicts, and file lists, so the resumed run **skips what already ran and re-enters at the failed stage**: a run that failed to commit commits and goes on to open the MR/PR, and one that failed on `build` re-runs the checks in the same worktree — fix the code there and resume. A run that never finished applying its diff re-reads the working tree (which a failed run no longer resets) and replays it into the reset worktree. Nothing about a successful run changes, and a run whose worktree you have since deleted still falls back to the existing origin-based resume/adopt paths. Two supporting fixes: the changelog stage no longer writes a second identical bullet when it re-runs, and a run that renamed its temp branch drops the stale temp-branch state file instead of leaving `sessions`/`resume` an entry pointing at a worktree that has moved on.
- **Behavior change: a run started from inside the TUI now stays on the alt screen for its whole duration**, instead of suspending to the plain terminal and handing it back afterward. Starting a run (or a session's resume/review) pushes a live dashboard screen — the same step tree, spinner, and token figures the plain CLI paints, ported to the TUI's own line-based renderer (`ui/runTreeFormat.ts`, shared by both) — and returns to the TUI once it settles, on any key. Non-interactive invocations (CI, piped output, `plainOutput`) are unaffected: they never touch the TUI and keep rendering exactly as before via `TreeRenderer`/`LineRenderer`. A finished run's narration no longer lands in your terminal's scrollback the way the old suspend-based design left it — `pipeline-worker sessions --branch <name>` (or the TUI's Sessions screen) has the full step-by-step record instead.
- **Behavior change: the standalone `pipeline-worker serve` MCP server has been removed**, along with its `@modelcontextprotocol/sdk` dependency. It duplicated what the `glab`/`gh` CLIs already do directly, and pipeline-worker's own forge access has always gone through them (GitLab) or a direct REST/GraphQL `fetch` (GitHub) rather than through this server. A CI-fix agent turn is now told to use the forge CLI (`glab`/`gh`) itself — it already runs with full, unrestricted tool access for exactly this reason. If you had registered `pipeline-worker serve` in an external agent's own MCP config, remove that entry; there is nothing left to connect to.
- **Behavior change: the reviewer now uses one agent session per MR/PR instead of one per file.** `chunkDiff` cuts the patch on file boundaries and never combined files, so `reviewChunkChars` acted as a *ceiling* for splitting a large file rather than a *target* for filling a turn — a 40-file MR of small edits spent 40 separate agent sessions on 7KB of diff, each re-paying the agent CLI's own system prompt and tool definitions. Chunks are now packed into turns up to the char budget (default raised to `200000`, ~50k tokens), so a normal MR/PR is reviewed in a single session and each file arrives as its own `--- File:` section, with the finding's `file` required to name the section its line came from. New setting **`reviewFilesPerTurn`** (default `0` = decide from the agent): a cloud model takes the whole diff, `little-coder` takes 3 files per turn clamped under its `maxPromptChars` (holding back room for the prompt's instructions, so its middle-out trim can never land inside a patch and renumber the lines a comment anchors to). Set a number to pin the group size for either. Findings are still gatekept against every commentable line in the whole diff, so a multi-file turn cannot anchor a comment onto the wrong file.
- **Per-step token figures now break down into input, cache, and output.** The dashboard showed one total per step, which counts prompt-cache reads at full weight — an agent loop re-sends its whole prompt on every internal turn, so a cheap intent capture could read as `101.7k tok`. Step rows now show `in 98.5k (92k cached) · out 3.2k`, and a settled run prints a per-turn table splitting fresh input from cache reads, cache writes, and completion. The claude adapter keeps `cache_read_input_tokens`/`cache_creation_input_tokens` as their own fields (still folded into `inputTokens`, so totals are unchanged); an adapter that reports no usage renders exactly as before.
- **Behavior change: every agent turn now runs with a per-step system prompt and a real tool gate.** Each `agent.invoke` passes a one-sentence `--system-prompt` stating only that turn's job, and names the tools it may use: intent capture gets `Read` alone (previously `Read`, `Grep`, `Glob`, `Bash(git diff:*)`), conflict resolution — both the diff-apply path and the CI-watch merge path — gets `Read`/`Write`/`Edit` and no shell at all, and the MR/PR reviewer gets `Read`. On `claude` the allowlist now becomes `--tools` (which built-in tools exist for the turn) as well as `--allowedTools` (which run unprompted), so a read-only turn cannot reach a shell by asking for permission that `--permission-mode acceptEdits` would grant. The CI-fix and local-check-fix turns are deliberately left unrestricted: fixing a red build means running the failing command.
- **Intent capture now gets the diff handed to it.** pipeline-worker runs `git diff <baseRef>` in the worktree and embeds the patch in the prompt (capped at 20000 chars, trimmed middle-out with a marker), so the step judges the *delta* — hunk headers, removed and added lines — rather than the post-change contents it would see if it could only read files, and it still needs no shell to get there. The changed-file list stays in the prompt because untracked files never appear in a diff, and `Read` remains available for those. Best-effort: a worktree git cannot diff (or an unresolvable base ref) degrades to a note plus the file list rather than failing the run.
- **Behavior change: the reviewer works from the diff, not from the files.** The reviewer's persona moved out of every chunk prompt into the turn's system prompt (it was being restated once per chunk), and the instruction that invited it to "read the surrounding files" is now the opposite: review the given diff, and drop a finding the diff alone cannot support. One review turn's context is bounded by `reviewChunkChars` again instead of by how large the touched files happen to be.
- **New setting `bareAgentMode` (default `true`):** runs `claude` with `--bare` — no hooks, no LSP, no plugin sync, no `CLAUDE.md` auto-discovery, no attribution — so a scripted turn carries only what it needs. **Set it to `false` if your Claude Code sign-in is a subscription rather than an API key:** `--bare` reads credentials only from `ANTHROPIC_API_KEY` (or an `apiKeyHelper` via `--settings`) and never from OAuth or the keychain. pipeline-worker warns at startup when bare mode is on and no key is exported, since otherwise every turn of the run fails with an opaque API error. Adapters with no equivalent flag (copilot, pi, little-coder) are unaffected beyond the system prompt they now receive.

- **Behavior change: configuration moved out of the environment into `~/.config/pipeline-worker/config.json`.** Every `PIPELINE_WORKER_*` environment variable is gone, and the repo-root `.env` file is no longer read; the first run creates the JSON file pre-filled with every default, and editing it configures every repo on the machine. Tokens live there too (`gitlab.token`, `github.token`), alongside the new `github.apiUrl` (GitHub Enterprise) — `GITHUB_TOKEN` is no longer consulted. Per-repo values keep auto-detecting exactly as before (`github.repo` from `origin`, `gitlab.projectId` from `gitlab.repoBase`, `build`/`lint`/`test` from the toolchain). **Migration:** run `pipeline-worker` once, then move each `PIPELINE_WORKER_FOO_BAR` value into its `fooBar` key (nested under `gitlab`/`github` for the forge settings) and drop the exports from your shell profile. A malformed or unreadable file warns and falls back to the defaults rather than failing the run, and `$XDG_CONFIG_HOME` is honored when set.
- **Behavior change: a finished run now leaves your repo on the feature branch it built** (new `switchToFeatureBranch` setting, on by default). Previously the run reset your repo and left you on the target branch, so making one more change to the same MR/PR meant checking the branch out by hand — the run's worktree being long deleted — or re-running pipeline-worker and getting a second, unrelated MR/PR. The branch swap happens last, after cleanup and the local target-branch sync, and is best-effort: a working tree that still has uncommitted changes is left untouched (with a note) rather than having them dragged across, and a failed checkout never fails an otherwise-green run. Set `"switchToFeatureBranch": false` for the old behavior.
- README updated to document auto-merge-on-green default, completion sound notifications, glab CLI integration, improved boolean parsing, and various reliability fixes from recent releases.
- **Behavior change:** `pipeline-worker run` now opens its MR/PR against origin's default branch — `main` or `master`, auto-detected — instead of whatever branch you happened to be standing on. Running from a feature branch previously opened a *stacked* MR/PR into that feature branch; it now targets trunk. Detection tries `refs/remotes/origin/HEAD` (re-validated against origin, so a stale ref left by a main/master rename can't become the target), then the remote's HEAD symref, then probes origin for `main`/`master` (when both exist, the one your HEAD's merge-base is closest to wins). Pass the new `pipeline-worker run --target <branch>` to choose the base explicitly — it's validated against origin before any worktree is created. Only when origin can't answer at all does the run fall back to the old behavior of targeting the current branch.
- **Behavior change:** a `pipeline-worker run` from a branch that already has an open MR/PR — the "reviewer left a comment, you fixed it, you ran it again" case — no longer opens a second MR/PR. The commit lands on that same branch (rebasing onto it first, so a fixup pushed there meanwhile isn't clobbered), and the run's file-wise breakdown is *appended* to the MR/PR description under a `🔁 Follow-up` heading rather than replacing what's already there. Auto-merge and the title are left as the humans left them, and `squashOnMerge` is skipped on this path so review comments stay anchored to their commits.
- Reorder workflow steps to run code quality checks before capturing intent and renaming the branch. This optimizes the fail-fast path: if checks fail, the workflow exits early without performing downstream operations.
- Renderer selection (the `plainOutput` setting vs. the live dashboard) is now a pure, independently-tested function, and the step-tree/renderer layer gained an edge-case test matrix: narrow and undefined terminal widths, resize mid-run, an unknown step id (never throws — the run keeps going), and the exact shape an escalated run leaves in the narration (the failing step and its `ci-watch` parent both marked failed, `merge` left pending).
- **Behavior change:** `autoMergeOnGreen` now defaults to `true` (was `false`). A `pipeline-worker run` now goes all the way to a merged PR/MR with your local target branch fast-forwarded, unattended, instead of stopping at "CI is green, merge it yourself." This remains best-effort — a forge that rejects auto-merge (required approvals, feature disabled, ...) leaves the run to finish normally and you merge manually, exactly as before. Set `"autoMergeOnGreen": false` to restore the previous default. Enabling `squashOnMerge` alongside the new default now prints a warning at startup, since the forge may merge (and delete) the branch before the squash push runs.

### Fixed

- **Behavior change: `reviewModel` now defaults to `sonnet` instead of to the agent CLI's own default.** An empty `reviewModel` sends no model flag at all, which handed the choice to `claude`'s own default — and that default tracks the newest, most expensive model, which an OAuth/subscription sign-in has no access to. The result was that `pipeline-worker review --branch <name>` (and the automatic review stage) failed outright on a fresh install for anyone signed in that way, with the agent CLI's model error rather than anything pipeline-worker could explain. The review turn now always passes `--model` explicitly, defaulting to `sonnet` — reachable on every tier and still well clear of `intentModel`'s `haiku`, which is the entire point of having a separate setting. `pi` and `little-coder` are unaffected: their CLI takes a `provider/id` rather than an alias, so they keep the adapter default. Setting `"reviewModel": ""` remains the documented escape hatch for "let the agent CLI pick", and is now honored as such instead of falling through to the default. **If you are signed in with OAuth, also check `bareAgentMode`:** it defaults to `true`, and `claude --bare` never reads OAuth or keychain credentials (pipeline-worker warns about this at startup).
- **Behavior change: GitLab review comments now land on the line they flag, instead of piling up as MR-level threads.** The position was passed as `glab api --field 'position[new_line]=42'` pairs, and glab keeps a bracketed key *literal* in the JSON body it builds (`{"position[new_line]": 42}`) — that is not the nested `position` hash the API declares, so GitLab discarded it and filed every review comment as an ordinary comment on the merge request with no file or line attached. The position now travels as bracketed query parameters, which GitLab parses into the nested hash, while the comment body (arbitrarily long, often carrying a suggestion block) stays in the JSON body. Two guards come with it: an MR that reports no `diff_refs` is refused before anything is posted, and a discussion GitLab accepted *without* a position is reported as a rejected comment rather than counted as posted — an unanchored note is the bug, not a result. `createInlineComment` also returns the note's numeric id now instead of the discussion's hash id. GitHub PR review comments were never affected.
- **Behavior change: a review finding is now anchored by the code it quotes, not only by the number it names.** Every finding must also carry `code`, the flagged added line copied verbatim, and the gate anchors the comment to the line that actually holds it: a number copied out of the wrong `--- File:` section (or off a neighbouring line) is corrected to the matching added line in the file the finding names, and a quote matching nothing falls back to the old number-only check. This is the mismatch weaker reviewers hit most — the old gate could only ask whether the number was *some* commentable line in that file, so a wrong-but-commentable number posted a comment on unrelated code. An agent that omits `code` is gated exactly as before.
- **`pipeline-worker resume` no longer refuses a run that died before its MR/PR existed.** A state file with no merge request recorded used to exit with `no resumable run found for branch X (no merge request recorded yet)` — which made *having* a state file strictly worse than having none, since a branch pipeline-worker had never seen was happily adopted. That is exactly the case that hits after a run pushes its branch and then loses the forge (a GitHub 500, a killed process, a dropped network): the work is safely on origin and adoption is precisely the code that turns such a branch into an open PR/MR. `resume` now falls through to adoption, reusing the dead run's target branch unless `--target` says otherwise, and announces itself as "Adopting a stalled run" so it is clear which recovery ran. A branch that was never pushed still stops, but now with a message that says so (`branch X does not exist on origin`) instead of a raw `git fetch` failure.
- The copilot agent adapter now honors per-invocation model selection (`intentModel`) via copilot CLI's `--model` flag, translating the Claude aliases `haiku`/`sonnet` to `claude-haiku-4.5`/`claude-sonnet-4.5` and passing any other value through verbatim, instead of ignoring the configured model with a warning.
- GitLab write requests now pass their body as `glab api --field`/`--raw-field` pairs instead of streaming raw JSON through `--input -`, fixing HTTP 415 errors on GitLab installations and proxies that reject the streamed body.
- GitLab API requests without a body (GETs, pipeline retry) no longer send `Content-Type: application/json`, fixing HTTP 415 errors on GitLab instances that reject body-less JSON requests.
- Boolean settings (`runLintAndTest`, `cleanupOnSuccess`, `cleanupEarly`, `updateChangelog`, `autoMergeOnGreen`, `squashOnMerge`) now accept `1`/`0`, `yes`/`no`, `on`/`off` and tolerate surrounding whitespace, on top of `true`/`false`. Anything else still falls back to the default but now prints a warning naming the key, instead of silently resolving to the default — `"runLintAndTest": "0"` previously ran lint and test anyway with no hint why.
- Added truncateToWidth() utility function to prevent spinner detail text from exceeding terminal width, preventing unwanted line wrapping. Integrated into runStep() render function to apply terminal-width-aware truncation.
- `watchPipeline` no longer polls the full 2-hour safety window before crashing when a GitLab pipeline ends in `manual` or `scheduled` status (e.g. a manual deploy gate after tests) — both are now recognized as terminal and escalate to a human immediately, same as `canceled`/`skipped`.
- Forge API calls (`forgeFetch`) now retry transient 429/5xx responses and network errors with bounded exponential backoff (honoring `Retry-After` on 429), instead of crashing the whole run on a single blip during a long CI-watch poll loop.
- CI-fix and merge-conflict-resolution now re-run build/lint/test locally before pushing, looping back to the agent on a local failure instead of spending a full remote CI round-trip to discover an obviously broken fix.
- `hasCiConfig` now checks a GitLab project's actual "CI/CD configuration file" setting (via a new `ForgeClient.getCiConfigPath`) in addition to the conventional `.gitlab-ci.yml` path, fixing a false "no CI configured" conclusion for projects using a custom path.
- This repo's own release workflow (`.github/workflows/ci.yml`): the `publish` job now serializes via a `concurrency` group and rebases before the version-bump push, fixing a race where two merges close together could fail the second one's push as non-fast-forward.
